The frontend starts keyword and semantic sections independently. 

function runSearch(query: string) {
    const requestId = ++searchRequestId;
    abortSearchRequests();
    retainedSearchQuery = query;
    pendingSearchQuery = query;

    const nextSections = createEmptySearchSections();
    nextSections.keyword.loading = true;
    nextSections.semantic.loading = semanticSearchEnabled;
    searchSections = nextSections;

    void runSearchSection(query, "keyword", requestId);
    if (semanticSearchEnabled) {
        void runSearchSection(query, "semantic", requestId);
    }
}

1. Keyword search

Keyword search starts with the words on the page.

It is the oldest, plainest retrieval path here. It finds chunks that contain query terms, then ranks them with text-search signals.

Prod docs Keyword Index FTS Leg Search API

Keyword search - fundamentals

FTS finds matches. BM25 ranks them.

Term Meaning Why it matters
FTS Full-text search: an index built for text lookup. Fast keyword retrieval over many chunks.
BM25 A relevance formula for keyword matches. Rewards rare, focused terms without overvaluing repetition.
Stemming Reducing word variants to a root-like form. runs, running, and run can match more flexibly.

Sources: docs/features/search.md:47-80, backend/src/services/fts.rs:282-393.

Keyword search - fundamentals

Stemming changes what the FTS index considers the same word family.

Tokenize

FTS splits text into searchable tokens. Punctuation, case, and word boundaries are normalized.

Stem

The porter tokenizer reduces English variants toward a common stem before storing and querying.

Match

BM25 ranks matching FTS rows after tokenization and stemming have made the candidate set.

FTS is the index and query engine. Stemming is one normalization step inside that engine.

Sources: backend/src/services/fts.rs:367-393, docs/features/search.md:47-80.

Code - keyword search

UNINDEXED means stored, but not full-text searchable.

Column kind What FTS does dAstIll use
Indexed text Tokenizes, stems, matches with MATCH, and contributes to BM25. chunk_text, video_title, section_title.
UNINDEXED Stores the value in the FTS row, but skips the full-text token index. IDs, source kind, channel name, publication date, timestamp.
Why Keeps metadata out of keyword ranking. Text ranks. Metadata labels and links.

Source: backend/src/services/fts.rs:367-393. dAstIll still uses metadata columns for result payloads and SQL filters; they are simply not part of the FTS token index.

Keyword search - dAstIll specifics

The FTS leg runs several lexical probes, then deduplicates by chunk.

Step Code path Effect
Phrase probes build_fts_phrase_queries from normalized and raw query. Exact phrase hits get first chance.
Strict probe "term" AND "term" from up to 4 meaningful terms. Keeps multi-term searches precise.
Relaxed probe "term" OR "term" when useful. Recovers partial matches for natural-language queries.
SQL filters source_kind and channel_id are normal filters, not FTS tokens. Metadata can constrain retrieval without polluting ranking.
Post-rank Dedup chunk ids, then promote phrase hits, summaries, term coverage, and title matches. BM25 remains useful, but app-specific relevance wins ties.

2. Semantic search

Semantic search starts with meaning.

It can find a relevant chunk even when the chunk does not use the same words as the query. It trades simplicity for model and vector infrastructure.

Prod docs Semantic Enablement Semantic Leg Search Embedding

Semantic search - fundamentals

Embeddings turn language into geometry.

Term Meaning Why it matters
Embedding A list of numbers representing text. Lets the system compare meaning by distance.
Vector search Finding nearby vectors. Retrieves conceptually similar chunks.
ANN Approximate nearest neighbor search. Speeds up vector lookup at scale.

Sources: docs/features/search.md:298-327, docs/pipelines/ai-models.md:89-117.

Semantic search - overlapping functionality

Semantic search overlaps with keyword search at the retrieval boundary.

Same chunks

Both retrieval modes search the derived projection built from transcripts and summaries.

Same filters

Both can respect source kind and channel filters before returning candidates.

Different weakness

Semantic search can miss exact names. Keyword search can miss paraphrases.

Normalization removes formatting before chunking.

fn normalize_source_text(input: &str) -> String {
    input
        .lines()
        .map(str::trim)
        .filter(|line| !line.is_empty())
        .map(strip_markdown_prefix)
        .collect::<Vec<_>>()
        .join(" ")
        .split_whitespace()
        .collect::<Vec<_>>()
        .join(" ")
        .trim()
        .to_string()
}

Semantic search - fundamentals

Exact scan means exact math, not exact equality.

Exact scan

Compute similarity against every candidate vector in scope. It can match near vectors, not only identical vectors.

ANN

Use an approximate nearest-neighbor index to skip most vectors. Fast, approximate by design.

dAstIll

The architecture names a hybrid_exact pre-ANN path. Current code uses it mainly as a mode label and tighter limit.

Exact scan is a vector-search term. In the current adapter, check the implementation before assuming local dot-product scanning.

Sources: docs/features/search.md:298-327, backend/src/handlers/search/mod.rs:139-276, backend/src/db/search.rs:694-711.

Semantic search - dAstIll specifics

ANN is not a local FTS-style index.

Question Answer
Where is ANN? In S3 Vectors, beside the stored vector records.
When is it not ready? Semantic search is off, no embedding model is configured, or the worker has not marked vector_index_ready.
Who marks ready? The backend checks S3 Vectors and sets vector_index_ready in search status.
When can it build? Only when auto-create is enabled, semantic search is enabled, ready sources exist, and pending/indexing backlog is small enough.
Current adapter note has_vector_index returns true and ensure_vector_index is a no-op in the checked-in S3 adapter.

Semantic search - dAstIll specifics

HyDE makes short semantic queries less thin.

HyDE means Hypothetical Document Embeddings. When the semantic HyDE gate passes, dAstIll can ask a model to write a brief imagined answer, then embed that passage instead of the raw query.

The raw query still drives keyword search. HyDE only changes the semantic embedding input.

Sources: docs/pipelines/ai-models.md:165-221, backend/src/services/search/mod.rs:472-545.

Semantic search - example

HyDE turns a short query into a richer vector probe.

Step Example dAstIll behavior
Raw query memory safety Two meaningful terms, so HyDE can trigger when configured.
Hypothetical passage A concise 2-3 sentence answer about preventing invalid memory access. Generated through Ollama /api/generate.
Embedding input The hypothetical passage. Semantic leg embeds this richer text.

3. Hybrid search

Hybrid search uses two imperfect signals and looks for agreement.

It keeps keyword precision and semantic recall in play at the same time.

Prod docs Query Path RRF Fusion Neural Reranker

Hybrid search - fundamentals

Fusion joins ranked lists without pretending scores are the same.

Term Meaning Use
Fusion Combining multiple ranked result lists. Turns keyword and semantic candidates into one order.
RRF Reciprocal Rank Fusion. Default hybrid merge. Also builds the shortlist before optional reranking.
Reranking Reordering an RRF shortlist with a stronger model. Runs only when a reranker model is configured and hybrid has both legs.

Sources: docs/features/search.md:329-353, docs/pipelines/ai-models.md:119-163.

Hybrid search - overlapping functionality

Hybrid search is where the overlap becomes the product.

Keyword-only wins

Exact names, acronyms, quoted phrases, and rare terms often belong to BM25.

Semantic-only wins

Paraphrases, broad concepts, and adjacent phrasing often belong to vectors.

Agreement wins

When both find the same chunk, RRF lifts it without comparing incompatible scores.

Sources: docs/features/search.md:329-375, backend/src/handlers/search/ranking.rs:137-225.

Hybrid search - dAstIll specifics

Hybrid has a sequential shell around two independent retrieval legs.

Sequential
Prepare request Normalize query, check channel access, read search status, resolve hybrid_exact or hybrid_ann, and compute candidate limits.
Independent legs
Keyword leg FTS5 MATCH, BM25, keyword pre-rank, snippet extraction, and access filter. The current handler runs this first.
Semantic leg Optional HyDE, query embedding, S3 vector query through hybrid_exact or hybrid_ann, and access filter. The current handler runs this second.
Sequential
Choose final rank One usable leg: group that leg. Both legs: RRF. Reranker configured: RRF shortlist, then cross-encoder rerank. Reranker failure: RRF.
Sequential
Group and rescue Group chunks by video, sort source matches, promote exact keyword rescue when needed, and return the search payload.

Sources: backend/src/handlers/search/mod.rs:170-411, docs/features/search.md:260-421.

Hybrid search - dAstIll specifics

RRF merges first. Rerank is optional.

Request state Final ordering path Reason
Keyword or semantic Single-leg order, with exact rescue where needed. RRF and rerank need a hybrid shortlist.
Hybrid, one leg empty or unavailable The remaining leg is grouped directly. There is nothing to fuse.
Hybrid, both legs, no SEARCH_RERANK_MODEL RRF is the final rank. RRF combines keyword rank and vector rank without comparing raw scores.
Hybrid, both legs, reranker configured RRF shortlist, then cross-encoder rerank. The reranker rereads query plus candidate text and returns a stronger order.
Reranker fails or returns empty RRF is used. Search degrades to the deterministic hybrid rank.

Sources: backend/src/handlers/search/mod.rs:363-411, backend/src/handlers/search/ranking.rs:178-250, docs/features/search.md:347-359.

Code - hybrid search

The request path resolves the effective retrieval mode.

fn resolve_requested_retrieval_mode(
    execution_mode: SearchExecutionMode,
    hybrid_configured: bool,
    vector_index_ready: bool,
) -> SearchRetrievalMode {
    if execution_mode == SearchExecutionMode::Keyword || !hybrid_configured {
        SearchRetrievalMode::FtsOnly
    } else if vector_index_ready {
        SearchRetrievalMode::HybridAnn
    } else {
        SearchRetrievalMode::HybridExact
    }
}

Query cleanup Drops wrappers like “show me videos about”. Keeps FTS terms sharp.
Term cap Uses up to 4 meaningful terms for FTS. Controls brittle long-query matching.
Phrase path Tries phrase queries and relaxed OR queries. Balances precision and recall.
Rescue path Promotes exact keyword hits when semantic order misses them. Protects entities, titles, and quoted phrases.

Hybrid search - query shaping

Conversational text becomes a bounded retrieval probe.

Mechanism Details
Tokenize and lowercase Split on punctuation except _, -, and ., so technical tokens such as GPT-4.1 survive.
Strip wrappers Remove leading phrases such as where they talk about and UI words such as videos.
Keep meaningful terms Drop stopwords; keep length 3+ plus short technical terms like ai, db, and ui.
Bound FTS Dedupe and keep the first four terms; build phrase queries, strict AND, and relaxed OR.
HyDE nuance The runtime HyDE gate checks this capped term list. The code follows the cap; docs describe short-query intent.

dAstIll architecture - RAG ranking

Chat ranking is rank fusion plus source-budget selection.

Mechanism Current code Result
Candidate limit ((budget * 2) / query_count), min 8, max 48; later passes get a small boost. Broad questions get more candidates without unbounded fan-out.
Rank score Each keyword or semantic batch contributes 1 / (60 + rank). Agreement across batches raises a chunk.
Combined score Keyword and semantic scores add when both exist. Hybrid evidence can beat one-sided evidence.
Diversity After max_per_video, same-video score is multiplied by 0.3^n; first opposite source kind gets 1.08x. Selected sources spread across videos and summary/transcript evidence.
Scope and preference Video focus gets 1.8x, channel focus 1.2x, recommendation wording can add a preference boost. Mentions and recommendation prompts bend ranking without bypassing access checks.

HyDE fails The raw query is embedded.

Glossary - data and indexing

Terms for how content becomes searchable.

Term Meaning
Canonical content The source transcript or summary owned by the library model.
Search projection Derived search data built from canonical content.
Chunk A retrievable text unit with metadata such as source kind and timestamp.
Normalization Plain-text cleanup before chunking.
FTS index The local full-text search table that stores searchable token structures.
Tokenizer The FTS component that splits text into searchable terms.

Sources: docs/features/search.md, backend/src/services/search/content_processing.rs.

Glossary - retrieval

Terms for how candidates are found and ranked.

Term Meaning
BM25 A keyword relevance formula used to rank FTS matches.
Porter stemming English word-family reduction inside the FTS tokenizer.
Embedding A numeric vector that represents text meaning.
Exact vector scan Exact similarity calculation against every candidate vector in scope.
ANN Approximate nearest-neighbor search for faster vector lookup.
Exact rescue Keyword safety path that promotes exact hits over weak semantic order.
RRF Reciprocal Rank Fusion, a rank-based way to merge retrieval lists.

Sources: docs/features/search.md:260-421, backend/src/handlers/search/mod.rs, backend/src/handlers/search/ranking.rs.

Glossary - RAG and runtime

Terms for how evidence becomes an answer.

Term Meaning
RAG Retrieval-augmented generation: retrieve evidence, then generate from it.
Grounding Selected evidence placed into the answer model context.
Retrieval pass One planned round of keyword and semantic searches.
Source budget The maximum evidence excerpts a chat turn tries to carry forward.
Reranker A model that rereads a shortlist and produces a better final order.
SSE Server-sent events for status, sources, tokens, and completion.
Trace Redacted record of plan, tools, retrieval counts, and budget use.
