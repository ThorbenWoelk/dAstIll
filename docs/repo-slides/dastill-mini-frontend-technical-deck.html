Scope

This deck explains the mini frontend only.

Backend details appear only where they define the frontend contract: payload shape, read-status endpoint, auth requirement, and the S3-backed read-state decision. The main workspace, queue, search, chat, and full backend pipeline stay out of scope.

Sources: .specs/dastill-mini/prd.md; .adr/adr-dastill-mini-uses-s3-read-state.md
Why mini exists

It is the small path through maintenance mode.

The PRD frames mini as a fallback when the full workspace is paused or unavailable. It keeps the public landing page in maintenance posture while giving signed-in users a focused way to read summaries from their subscribed channels.

No full workspace No search dependency No chat surface No new visual system
Sources: .specs/dastill-mini/prd.md; frontend/src/lib/components/home/MaintenancePage.svelte

Auth and load lifecycle

The route waits for auth before touching reader data.

  1. authState.ready gates the initial decision.
  2. Unauthenticated users are sent to /login?redirectTo=%2Fmini.
  3. Authenticated users call mini.loadReader().
  4. Loading, error, empty, and active-summary branches render from controller state.
  5. Retry calls loadReader(mini.selectedChannelId) to preserve channel intent.
Sources: frontend/src/routes/mini/+page.svelte; frontend/src/lib/auth-state.svelte.ts

Controller state

MiniReaderState is the real frontend model.

The controller stores the payload, selected channel, active video, loading and error state, unread filter, mutation flags, read progress, content key, and highlight controller. It also derives visible summaries, active index, active summary, rendered markdown, navigation affordances, unread count, and filter count.

Sources: frontend/src/lib/mini/mini-reader-state.svelte.ts
Selection rules

Mini defaults to unread-first navigation.

Initial pick chooseActiveVideoId keeps a preferred id, else first unread, else first summary.
Filter showUnreadOnly defaults true, so visibleSummaries can be smaller than the payload.
Reconcile The route calls reconcileActiveVideo() after reader changes so active id stays visible.
Advance Mark-read-and-advance looks for the next unread summary with wraparound.
Sources: frontend/src/lib/mini/mini-reader-state.svelte.ts; frontend/tests/mini-reader-state.test.ts
Read mutation

Read status is optimistically reflected after the server writes.

  1. User clicks Mark as read, the bottom checkbox, or presses r.
  2. Controller guards against duplicate mutation with markingRead.
  3. Frontend sends PUT /api/mini/videos/{id}/read.
  4. On success, the local reader payload is replaced with that summary marked read.
  5. Active video is recalculated and contentKey increments to restart article rendering.
Sources: frontend/src/lib/mini/mini-reader-state.svelte.ts; frontend/src/lib/api.ts
Highlight integration

Mini reuses the workspace highlight controller.

The mini controller creates a home-workspace highlight controller, pins its content mode to summary, hydrates highlights for the active video on demand, filters out transcript highlights, and passes summary-only highlights into TranscriptView.

Sources: frontend/src/lib/mini/mini-reader-state.svelte.ts; frontend/src/lib/components/mini/MiniArticle.svelte; frontend/tests/mini-reader-state.test.ts
Article rendering

The article is a markdown reader wrapped around shared transcript UI.

  • renderMarkdown produces HTML from summary content.
  • MiniArticle displays thumbnail, channel, date, title, read state, source link, and body.
  • TranscriptView renders markdown and handles highlight selection.

Why contentKey matters

The article is wrapped in a keyed block so summary changes reset local DOM state and replay the entrance animation.

Sources: frontend/src/lib/components/mini/MiniArticle.svelte; frontend/src/lib/mini/mini-reader-state.svelte.ts
Scroll model

Scroll does two jobs: progress and bottom-bar mode.

The route owns a scroll container. On every scroll it updates normalized read progress and records whether the summary has moved more than 12 pixels from the top. That second flag swaps the bottom center control from channel picker to read checkbox.

Sources: frontend/src/routes/mini/+page.svelte; frontend/src/lib/components/mini/MiniTopBar.svelte; frontend/src/lib/components/mini/MiniBottomBar.svelte

Design contract

Mini follows the local system, with a few technical pressure points.

  • Aligned: muted palette, content-first layout, mobile bottom bar, bottom sheet, shared icons, skeleton loading, safe-area padding.
  • Worth checking: MiniTopBar filter button is 34px, while the design guidance asks mobile filter triggers to have a 44px touch target.
  • Worth checking: current mini CSS uses visible borders on top, bottom, strip, and sheet rows. They are structural, but the local system asks for a low border budget.
  • Worth checking: source code uses negative letter spacing in several mini headings, while this deck avoids it for portability.
Sources: design.md; frontend/src/lib/components/mini/*.svelte

Failure modes

The sharp edges are mostly integration edges.

  • Auth delay: route must not fetch until auth state is ready.
  • Cached stale reads: read mutation invalidates /api/mini, but local payload is also updated immediately.
  • Filtered active id: unread filter can remove the active item, so reconciliation is required.
  • Highlight scope: mini must only surface summary highlights, not transcript highlights.
  • Backend dependency mismatch: the frontend contract assumes mini avoids workspace bootstrap, but the backend still defines what "readable summary" means.

Extension points

Keep additions at the controller boundary.

New mini behavior should usually enter through MiniReaderState first, then fan out into small render components. That preserves the route as wiring, keeps async state transitions centralized, and matches the repo rule that reactive controller methods are the valid write path.

Sources: design.md; frontend/src/lib/mini/mini-reader-state.svelte.ts; frontend/src/routes/mini/+page.svelte

Open questions

The next technical pass should verify behavior in a browser.

  • Should mini get a dedicated Playwright spec for auth redirect, unread filter, channel sheet, and mark-read persistence?
  • Should MiniTopBar filter touch target be raised to 44px without making the bar feel heavy?
  • Should the active-summary selection survive route reloads or channel changes through URL state?
  • Should read progress ever auto-mark read, or stay explicit only as the PRD requires?
  • Should mini eventually stop depending on backend video lookup for read writes, to fully match the ADR direction?
